## Implemented flow

1. An administrator checks an actual therapist's external credential, then calls `POST /api/governance/credentials` with the therapist ID, `reference`/`canary`/`clinical` scope, evidence SHA-256, and a non-secret external reference. A self-registered therapist account is not enough. Revocation is append-only at `POST /api/governance/credentials/{therapist_id}/{scope}/revoke`.
2. A real caregiver may register a hash-bound consent receipt using `POST /api/governance/consents`. It remains `pending_verification` until a separate administrator checks both guardian relationship and applicable ethics documentation at `POST /api/governance/consents/{receipt_id}/verify`, or records a reason-coded `rejected` decision at `POST /api/governance/consents/{receipt_id}/reject`. The caregiver can withdraw at `POST /api/governance/consents/{receipt_id}/withdraw`. No consent is backdated to earlier recordings. Store the actual documents only in the approved external evidence location, not in this repository or product database.
3. Generate a metadata-only candidate packet with `python scripts/model/prepare_review_batch.py --kind reference --input <source-manifest> --output <new-packet.json>`. The packet is **not** an approval. An administrator imports it with `POST /api/governance/batches`. A credential-verified therapist reviews each actual local audio clip outside the child app, then posts each exact observed SHA-256 and decision at `POST /api/governance/batches/{batch_id}/decisions`. An administrator exports the completed signed record from `GET /api/governance/batches/{batch_id}/export`. Changed audio/source hash, revoked qualification, duplicate decisions, or incomplete review fail closed.
4. For canaries, generate a candidate packet with `--kind canary` and pass each fitting/reference/calibration source to `--forbidden-manifest`. After qualified review, run `python scripts/model/finalize_canaries.py --candidate-suite <candidate.json> --approval-export <signed-export.json> --output <new-approved-suite.json>`. The finalized suite contains both the signed human review and an exact-content signature. Stage an engineering bundle, run its technical canaries, then rebuild a production candidate from the exact approved suite and successful run. Neither a boolean flip nor a technical pass alone is approval.
5. For clinical content, prepare a manifest mapping exactly these ten names to relative files under `--clinical-root`: `vocabulary`, `tamil_prompts`, `voice_assets`, `avatar_states`, `result_wording`, `action_set`, `difficulty`, `retry_break_limits`, `test_protocol`, `limitations`. Run `prepare_review_batch.py --kind clinical --input <manifest.json> --clinical-root <content-root> --child-id <assigned-child-id> --output <new-packet.json>`. Only the separately credential-verified *currently assigned* therapist can approve the exact hash-bound bundle.
6. Every assigned child gets a 14-day checkup clock from the assignment time or latest therapist-confirmed completion. `GET /api/appointments/checkup-status` reports the real state. A caregiver requests one at `POST /api/appointments/checkups`; only the assigned therapist can confirm/complete it. Overdue means reminder and booking, while practice remains available. Unknown legacy assignment dates are not invented.

The backend uses `VAAKMITRA_REVIEW_SIGNING_KEY` (at least 32 UTF-8 bytes) for review exports and release verification. Provision it through the host secret manager; do not commit it or print it in review packets. A missing/changed key fails review verification and production readiness. Review exports contain hashes and reviewer IDs, not audio or scanned documents.

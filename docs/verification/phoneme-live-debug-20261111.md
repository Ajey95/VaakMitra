# Live phoneme diagnosis — recognition remains unreliable

The user's reported inconsistent live phonemes were a real quality problem. Earlier APK installation, three native fixture tests and a displayed preview established execution only. They did not establish live phonetic accuracy. **No accepted replacement or general recognition fix was delivered in this experiment.** The V7 model remains retained; privacy-hardened tools are recorded separately, and the new candidate was used only in the separate diagnostic test APK.

The operator explicitly chose phone-memory-only recording. Fifteen foreground trials were user-triggered with Record buttons, five prompts repeated three times. Actual recordings lasted about2.46–2.54seconds, were processed in phone memory, and the returned recording buffer was erased. The reviewed historical code had a UI-stall limit defect; future diagnostic capture is capped at40000samples with a separate2.5s deadline. No user audio files or predicted phoneme strings were saved, exported or used for training. Only prompt IDs, numeric comparison counts and processing conditions were retained.

The controlled Amma trials matched3/3 on unchanged V7. Their detected active windows were about600–620ms, compared with often1–2seconds in the earlier user-reported failing attempts. That is consistent with a pace/recording-condition sensitivity, but does not isolate a unique cause or mean a user must speak unnaturally fast. The phone microphone produced non-silent samples with strong VAD detection, and the pinned native fixture/decoder paths matched. A simple permission, silent-input or token-index-mapping failure was not established.
